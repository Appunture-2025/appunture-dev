\chapter{TECNOLOGIAS E ARQUITETURA DO SISTEMA} \label{cha:tecnologias}

Este capítulo apresenta o \textit{stack} tecnológico utilizado no desenvolvimento do \textit{Appunture}, detalhando a arquitetura do sistema, as tecnologias empregadas e as decisões técnicas que fundamentam a implementação da solução.

\section{VISÃO GERAL DA ARQUITETURA} \label{sec:visao_arquitetura}

O \textit{Appunture} foi desenvolvido seguindo uma arquitetura híbrida distribuída, composta por quatro camadas principais:

\begin{itemize}
    \item \textbf{Aplicativo Móvel (React Native + Expo)}: Interface principal do usuário com persistência local (SQLite) para resiliência em redes instáveis e mecanismo de enfileiramento para sincronização com o backend em nuvem;
    \item \textbf{API Backend (Java + Spring Boot)}: Servidor de aplicação responsável pela lógica de negócio, sincronização e Inteligência Artificial;
    \item \textbf{Ferramentas de Apoio (Python/HTML)}: Scripts de migração de dados e ferramenta de mapeamento de pontos (Point Mapper).
\end{itemize}

Esta arquitetura garante alta disponibilidade, performance otimizada e experiência consistente mesmo em ambientes com conectividade limitada.

\subsection{Diagrama de Arquitetura}

O \textit{Appunture} foi desenvolvido seguindo uma arquitetura híbrida e modular, que integra funcionalidades \textit{offline} e \textit{online} para garantir alta disponibilidade, desempenho e usabilidade mesmo em ambientes com conexão limitada ou instável.

\section{ARQUITETURA HÍBRIDA (PERSISTÊNCIA LOCAL E BACKEND EM NUVEM)} \label{sec:arquitetura_hibrida}

\subsection{Persistência Local e Enfileiramento de Operações}

O aplicativo móvel implementa persistência local (SQLite) para garantir performance e resiliência em redes instáveis. O código evidencia uma arquitetura cloud-backed em que o Google Cloud Firestore funciona como fonte de verdade, enquanto o cliente mantém cópias locais para leitura rápida e enfileira gravações para sincronização posterior.

            \textbf{Banco de Dados Local (SQLite):}
\begin{itemize}
    \item Armazena os pontos do atlas, pontos extras, sintomas e metadados necessários para renderização e consultas rápidas;
    \item Mantém dados do usuário (favoritos, notas) e tabelas de controle de sincronização (\texttt{sync\_queue}, \texttt{image\_sync\_queue});
    \item Estrutura otimizada com migrações e seeds para inicialização consistente;
    \item Fornece performance de leitura local e resiliência quando a rede está indisponível; operações de escrita do usuário são enfileiradas para envio ao backend quando houver conectividade.
\end{itemize}

    \textbf{Nota:} A busca inteligente por sintomas (assistente de IA) e outras funcionalidades que dependem de chamadas a serviços externos (IA, uploads de mídia) requerem conexão com a internet. Quando não houver conectividade, o usuário pode acessar apenas o conteúdo disponível localmente; gravações e uploads aguardam até que a sincronização ocorra.

    \textbf{Sistema de Armazenamento Seguro:}
\begin{itemize}
    \item \textbf{SecureStore}: armazenamento criptografado para tokens e credenciais sensíveis;
    \item \textbf{AsyncStorage}: persistência de configurações e dados não sensíveis;
    \item Cache de imagens e recursos visuais via sistema de arquivos para melhorar latência de renderização;
    \item Persistência de estado via \textit{middleware persist} do Zustand integrada ao AsyncStorage para conservar preferências e estado de UI.
\end{itemize}

\subsection{Sincronização Inteligente}

Quando conectado à internet, o sistema implementa sincronização bidirecional automática:

\textbf{Sincronização Descendente (Backend $\rightarrow$ Mobile):}
\begin{itemize}
    \item Atualização automática de dados do atlas;
    \item \textit{Download} incremental baseado em versionamento;
    \item Compressão de dados para otimizar transferência;
    \item Validação de integridade dos dados recebidos.
\end{itemize}

\textbf{Sincronização Ascendente (Mobile $\rightarrow$ Backend):}
\begin{itemize}
    \item \textit{Upload} de favoritos do usuário;
    \item \textit{Backup} automático de preferências;
    \item \textit{Logs} de uso para análise de performance;
    \item Controle de conflitos com \textit{timestamp}.
\end{itemize}

\subsubsection{Atlas Anatômico (PNG + SVG sobreposto)}

Cada layer do atlas empacotado no bundle (\texttt{static/body-map/}) é composto por dois artefatos: um arquivo PNG para renderização visual e um arquivo SVG invisível, sobreposto e sincronizado na mesma escala, responsável apenas pela definição de hotspots e pela captura de interações por toque.

As funções utilitárias em \texttt{utils/svgAssets.ts} e \texttt{utils/bodyMap.ts} gerenciam o pré-carregamento e a coerência entre esses dois artefatos:

\begin{itemize}
    \item O PNG é usado exclusivamente para renderização visual e otimizado para rápido carregamento;
    \item O SVG sobreposto contém as formas vetoriais que definem as áreas interativas (hotspots) e permanece invisível ao usuário, servindo apenas para detecção de toques e mapeamento de coordenadas;
    \item As rotinas sincronizam escala e \texttt{viewBox} entre o PNG e o SVG para garantir que os hotspots estejam sempre alinhados à representação visual;
    \item Componentes como \texttt{BodyMap} e \texttt{BodyMapInteractive} consomem ambos os arquivos: renderizam o PNG e utilizam o SVG para interpretar interações, mantendo separação clara entre visualização e lógica de entrada.
\end{itemize}

Essa abordagem separa claramente a camada visual da camada de interação, melhora desempenho e reduz riscos de inconsistência entre visual e zonas de toque.

\subsection{Backend API (Java + Spring Boot)}

O \textit{backend} do projeto é implementado em Java com Spring Boot conforme o arquivo \texttt{backend-java/pom.xml}:

\begin{itemize}
    \item \textbf{Spring Boot}: 3.2.5;
    \item \textbf{Java}: 17 (LTS);
    \item \textbf{Spring AI}: versão definida no projeto (ex.: \texttt{spring-ai 1.0.0-M4}) para integração com provedores de LLM;
    \item \textbf{Google Cloud Firestore}: cliente \texttt{google-cloud-firestore} (3.x) usado como repositório principal;
    \item \textbf{Firebase Admin SDK}: usado para integrações com Storage e Auth do Firebase;
    \item \textbf{Bucket4j}: para rate limiting;
    \item \textbf{Caffeine / Micrometer / Logstash encoder}: para cache, métricas e logs estruturados.
\end{itemize}

As classes e dependências mostram que o \textit{backend} está preparado para:
\begin{itemize}
    \item expor APIs REST (OpenAPI disponível via springdoc);
    \item validar tokens Firebase/JWT e aplicar regras de segurança com Spring Security;
    \item integrar com serviços de IA via Spring AI (ex.: Vertex AI / Gemini);
    \item armazenar e sincronizar dados de pontos, sintomas e relações no Firestore.
\end{itemize}

\subsection{Banco de Dados e Persistência Local}

No aplicativo móvel, a persistência local é implementada com \texttt{expo-sqlite} e um conjunto completo de migrações e seeds (implementados em \texttt{services/database.ts} e \texttt{assets/data}). Pontos importantes observados no código:

\begin{itemize}
    \item Esquema local robusto com tabelas para \texttt{points}, \texttt{symptoms}, \texttt{symptom\_points}, \texttt{favorites}, \texttt{sync\_queue} e \texttt{image\_sync\_queue};
    \item Mecanismo de migração que detecta esquemas legados e realiza migrações automatizadas;
    \item População inicial (seed) carregada a partir de \texttt{assets/data} se necessário;
    \item Filas de sincronização locais (\texttt{sync\_queue} e \texttt{image\_sync\_queue}) com retry, contagem de tentativas e marcação de erro para garantir confiabilidade das operações offline$\rightarrow$online;
    \item Suporte a operações idempotentes e controle de conflitos básico por \texttt{timestamp} e operações tipo (UPSERT/DELETE).
\end{itemize}

No \textit{backend}, a persistência principal é feita no Google Cloud Firestore, que centraliza o conteúdo oficial e permite sincronizações incrementais com os clientes.

\subsection{Deploy e Integração com Google Cloud Run e Firebase} \label{sec:cloudrun_firebase}

O projeto é preparado para deploy containerizado no Google Cloud Run e faz uso dos serviços Firebase (Auth, Storage) e Google Cloud Firestore conforme a configuração presente no repositório. Abaixo estão os pontos observados diretamente no código e scripts:

\begin{itemize}
    \item \textbf{Build e deploy automatizados (Cloud Build):} O arquivo \texttt{backend-java/cloudbuild.yaml} constrói a imagem Docker no diretório \texttt{backend-java}, rotula a imagem como \texttt{gcr.io/\$PROJECT\_ID/appunture-backend:\$BUILD\_ID} e \texttt{:latest}, envia para o Container Registry e em seguida chama \texttt{gcloud run deploy} apontando para a imagem publicada. O passo de deploy seta variáveis de ambiente essenciais (ex.: \texttt{SPRING\_PROFILES\_ACTIVE=prod}, \texttt{FIREBASE\_PROJECT\_ID}) e configura recursos (memória 1Gi, CPU 1, concorrência, \texttt{port=8080}).

    \item \textbf{Script de deploy local/CI:} Existe um script de deploy (\texttt{backend-java/deploy.sh}) que executa \texttt{gcloud builds submit --config cloudbuild.yaml} e recupera a URL do serviço Cloud Run, além de suportar mapeamento de domínio e verificações pós-deploy.

    \item \textbf{Configurações do serviço Cloud Run (backup):} O repositório contém um backup de configuração de serviço (\texttt{cloud-run-config-backup.yaml}) e instruções em \texttt{CLOUD\_RUN\_BACKUP\_README.md} para restaurar as configurações com \texttt{gcloud run services replace}.

    \item \textbf{Variáveis e segredos:} O exemplo \texttt{.env.example} documenta variáveis esperadas no ambiente Cloud Run (ex.: \texttt{FIREBASE\_SERVICE\_ACCOUNT\_KEY}, \texttt{FIREBASE\_ENABLED}, \texttt{GOOGLE\_AI\_API\_KEY}). O deploy via Cloud Build / gcloud recomenda o uso do Secret Manager ou \texttt{--set-env-vars} para injetar segredos/credenciais em tempo de execução, em vez de armazená-los no código.

    \item \textbf{Inicialização do Firebase no backend:} A classe \texttt{FirebaseConfig.java} implementa uma estratégia robusta para carregar credenciais do Firebase, com prioridade:
        \begin{enumerate}
            \item conteúdo JSON do service account passado via variável de configuração (\texttt{firebase.service-account-key});
            \item caminho para arquivo local (\texttt{firebase.service-account-key-path});
            \item conteúdo JSON via \texttt{GOOGLE\_APPLICATION\_CREDENTIALS} (útil em CI/CD/Cloud Run quando o segredo é injetado como valor de ambiente);
            \item Application Default Credentials (ADC) quando disponível — padrão recomendado para Cloud Run usando Identity and Access Management (IAM) e Workload Identity.
        \end{enumerate}
        A inicialização remove prefixos \texttt{gs://} no nome do bucket, configura \texttt{FirebaseOptions} (projectId, storageBucket, credentials) e registra \texttt{FirebaseAuth} como bean para uso nos serviços de autenticação.

    \item \textbf{Integração com Firestore e Storage:} No \texttt{pom.xml} e na configuração são usadas as dependências \texttt{google-cloud-firestore} e \texttt{firebase-admin} — o backend usa Firestore como repositório primário e Firebase Storage para assets (quando habilitado). As chamadas e migrações esperam que as credenciais apropriadas estejam presentes no ambiente do Cloud Run.

    \item \textbf{Vertex AI / Gemini e credenciais:} Existem scripts e utilitários (ex.: \texttt{fix-vertex-ai-credentials.ps1}) que orientam a configuração das credenciais do Vertex AI no Cloud Run. O projeto recomenda evitar a exposição direta de um arquivo de chave no container e, em vez disso, usar ADC ou Secret Manager/Workload Identity para conceder permissões ao serviço.

    \item \textbf{Saúde e observabilidade:} O backend expõe endpoints de health para serviços IA (ex.: \texttt{/api/chat/health} no serviço de chat) e está preparado para integração com métricas/monitoramento (Micrometer/Prometheus) e logs estruturados (Logstash encoder). Cloud Run coleta logs e métricas automaticamente, facilitando a observabilidade.
    \item \textbf{Recomendação do fluxo de credenciais para Cloud Run:}
        \begin{itemize}
            \item Em produção use Workload Identity / ADC para que o serviço Cloud Run tenha permissões IAM adequadas para acessar Firestore, Storage e Vertex AI sem necessidade de arquivos JSON no container;
            \item Para CI (Cloud Build) injetar o conteúdo do service account via Secret Manager e configurar \texttt{GOOGLE\_APPLICATION\_CREDENTIALS} como variável de ambiente apontando para o JSON ou para o próprio conteúdo (o código trata ambos os casos);
            \item Evitar commit de chaves ou colocar arquivos de credencial dentro do repositório.
        \end{itemize}

    \item \textbf{Recursos e limites:} A configuração padrão de deploy via \texttt{cloudbuild.yaml} define limites conservadores (1Gi RAM, 1 CPU, concurrency 100, max-instances 10) para manter custos baixos (Cloud Run free tier/baixo custo) e comportamento previsível durante picos.
\end{itemize}

Em suma, o repositório mostra uma integração madura entre Cloud Run e Firebase: o backend é empacotado como container, publicado em Container Registry e implantado no Cloud Run; as credenciais e configurações do Firebase são carregadas dinamicamente (variáveis/Secret Manager/ADC); Firestore é usado como fonte de verdade e Firebase Storage é configurável para armazenar assets (SVGs, thumbnails) quando necessário.

\section{INTELIGÊNCIA ARTIFICIAL E SUPORTE À CONSULTA} \label{sec:ia}

O projeto utiliza uma abordagem RAG (Retrieval-Augmented Generation) orquestrada no \textit{backend}. As evidências no código-base mostram:

\begin{itemize}
    \item Integração com Spring AI e dependência específica para Vertex AI / Gemini, permitindo chamadas ao modelo de linguagem multimodal (Gemini) via adaptadores Spring AI;
    \item Serviço \texttt{AiChatService} e controlador \texttt{AiChatController} que expõem endpoints de chat e health-check (ex.: \texttt{/api/chat/health});
    \item Construção de contexto a partir de pontos e sintomas (recuperação de documentos relevantes) antes de enviar prompts enriquecidos ao modelo;
    \item Tratamento de logs e health checks para depuração e validação operacional do serviço de IA (conforme implementado no serviço de chat).
\end{itemize}

Essa arquitetura RAG reduz alucinações ao fornecer contexto verificado ao modelo e oferece rastreabilidade das fontes utilizadas nas respostas.

\section{TECNOLOGIAS DE SUPORTE} \label{sec:suporte}

\subsection{Gerenciamento de Estado (Mobile)}

O gerenciamento de estado global da aplicação é realizado através de bibliotecas modernas que oferecem alta performance e integração nativa com React.

\textbf{Zustand 4.4.7:}

Zustand é uma biblioteca de gerenciamento de estado minimalista baseada em \textit{hooks}, escolhida por sua simplicidade e performance superior. O sistema utiliza cinco \textit{stores} principais:

\begin{itemize}
    \item \textbf{authStore}: Gerencia autenticação via Firebase, armazenamento de tokens JWT e dados do perfil do usuário. Implementa login com email/senha e Google OAuth;
    \item \textbf{pointsStore}: Controla pontos de acupuntura e sistema de favoritos com \textit{optimistic updates} --- a interface atualiza imediatamente enquanto a operação é processada em segundo plano, com \textit{rollback} automático em caso de falha;
    \item \textbf{symptomsStore}: Gerencia lista de sintomas, categorias e relações com pontos de acupuntura;
    \item \textbf{syncStore}: Coordena sincronização \textit{offline}/\textit{online} através de fila de operações (\texttt{sync\_queue}) com controle de conflitos baseado em \textit{timestamp} e \textit{retry} com \textit{exponential backoff};
    \item \textbf{themeStore}: Controla tema visual da aplicação (claro/escuro/sistema) com persistência automática.
\end{itemize}

A persistência do estado é realizada através do \textit{middleware} \texttt{persist} do Zustand, integrado ao AsyncStorage para dados não sensíveis.

\textbf{React Query (@tanstack/react-query) 5.x:}
\begin{itemize}
    \item \textit{Cache} inteligente de requisições HTTP com invalidação automática;
    \item \textit{Refetch} estratégico baseado em foco da janela e reconexão;
    \item Suporte a operações \textit{offline} com sincronização em segundo plano;
    \item Deduplicação automática de requisições simultâneas.
\end{itemize}

\subsection{Ferramenta de Mapeamento de Pontos (Point Mapper)}

O Point Mapper é uma ferramenta web auxiliar desenvolvida em HTML, CSS e JavaScript puro, utilizada para mapear as coordenadas dos pontos de acupuntura sobre os artefatos do atlas (PNG visual e SVG de interação), aproveitando o SVG para captura precisa de coordenadas.

\textbf{Funcionalidades:}
\begin{itemize}
    \item Seleção de meridiano e ponto a ser mapeado;
    \item Seleção da vista anatômica (anterior, posterior, lateral, etc.);
    \item Clique na imagem para definir coordenadas em formato percentual;
    \item Prévia do marcador na posição selecionada;
    \item Exportação dos mapeamentos em formato JSON.
\end{itemize}

A gestão dos dados do sistema (pontos, sintomas, usuários) é realizada diretamente através das APIs REST protegidas do \textit{backend} e dos consoles administrativos do Firebase e Google Cloud Platform.
